# Security notes

This widget runs inside `plasmashell`, as your user, so it can read every file
you can read. The only real security property is that the code is small enough
to audit and that it does not send credentials anywhere except the provider
that issued them. This document states exactly what it touches.

See [`docs/SECURITY_AND_CREDENTIALS.md`](docs/SECURITY_AND_CREDENTIALS.md) for the complete Proxy mode credential ownership model and threat model (DNS rebinding, CSRF/CSWSH, SSRF, symlink/path traversal, secret redaction).

Background polling (`ai_limits.py`) remains read-only for Codex, Grok, Cursor,
Muse, Kimi, Qwen, and OpenCode credentials. Live CLI credential stores
(`~/.codex/auth.json`, `~/.claude/.credentials.json` + `oauthAccount` in
`~/.claude.json`, Secret Service `gemini/antigravity` via stdin to
`secret-tool store`, `opencode.db` via `opencode auth switch`, `~/.qwen/oauth_creds.json`,
`~/.config/muse/auth.json`, `~/.kimi-code/credentials/kimi-code.json`,
`~/.grok/auth.json`, or `~/.codexbar/config.json`) are written **only** when
you explicitly trigger an account switch, API-key add, or native login action
in `oasis_accounts.py`. Before switching away, the current live credential is
synced back to its vault snapshot so CLI-rotated tokens are never lost. The
Antigravity cache never contains the refresh token.

## Deliberate non-features

### No refresh of uncoordinated rotating tokens

Codex, Grok and Cursor use rotating, single-use refresh tokens without a shared
cross-process refresh lock. If a monitor refreshes one while the owning CLI
holds the old token, the next CLI call can fail and the user is signed out. The
widget therefore treats an expired access token as `expired` and lets the real
client renew it.

Claude Code uses explicit cross-process lock directories
(`~/.claude/.oauth_refresh.lock` and `~/.claude.lock`) and compare-and-swap
updates on `~/.claude/.credentials.json`, so the helper follows that exact
protocol when Claude's ~8h access token expires.

Antigravity is different: Google OAuth refresh tokens are long-lived and are
not rotated by a refresh, so refreshing is safe and is the only way to read
quota after the ~1h access token expires. The refreshed access token is cached
privately and never written back to the keyring.

### No auto-update

The widget never downloads code, checks a release feed, or runs an updater.
Updating means editing this checkout and running `./install.sh` again.

### No external CLI

No `codexbar`, `brew`, `pip`, `npx`, or downloaded binary is used. The helper is
Python 3 standard library only. `secret-tool` is the standard Secret Service
client and is invoked with `lookup` only (no `store`) for Grok/Cursor/
Antigravity reads; `sqlite3` is Python's stdlib module.

## Hardening in the helper

* Exact-host allowlist before every request.
* Redirects refused (`HTTPRedirectHandler.redirect_request` raises), so a 302
  cannot forward the bearer token to another origin.
* `ProxyHandler({})`: `http_proxy`/`https_proxy` environment variables cannot
  redirect token-bearing requests through a local proxy.
* Response bodies are capped at 4 MiB; credentials at 4 MiB.
* Errors expose only HTTP status codes, never response bodies or tokens.
* `secret-tool` is executed without a shell, with a 5s timeout, and the secret
  is read from stdout — never placed in argv.
* Temp cache files are per-PID and `0600`; the credential files are opened
  read-only.
* No shell profile is sourced (unlike some widgets that query the login shell
  for `PATH`).

## What this does not protect against

* A compromised `plasmashell`, Qt/Kirigami, Python, or `secret-tool`.
* A malicious same-user process: it can read the same credential files and the
  cache. The cache contains no tokens, but the credential files do.
* Provider-side compromise or a malicious response; the parsers only extract
  numbers and timestamps, and never execute response content.
* A modified copy of this checkout. Verify with `git diff` / `git log` if you
  keep it in version control.

## Audit checklist

```sh
# 1. All outbound hosts
grep -n "ALLOWED_HOSTS" -A16 package/contents/code/ai_limits.py

# 2. No writes to credential files
grep -n "open(.*[\"']w\|write_text\|os.replace\|chmod" package/contents/code/ai_limits.py

# 3. No shell execution
grep -n "shell=True\|os.system\|popen" package/contents/code/ai_limits.py

# 4. Live connections
strace -f -e trace=connect python3 package/contents/code/ai_limits.py fetch

# 5. What the panel will display (no secrets)
python3 package/contents/code/ai_limits.py fetch --pretty
```

If you want zero network access for a test, run the helper with
`unshare -rn python3 ... fetch`; every provider then reports `unreachable` and
the cache fallback is exercised.

## Reporting

This is a personal project. If you find a credential leak or an unintended
host, open an issue with the exact command and observation; do not paste real
tokens.
